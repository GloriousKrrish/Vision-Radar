## 1. Executive Summary

VisionRadar takes fixed-camera traffic video and produces tracked vehicles, calibrated road-plane trajectories, speed estimates with uncertainty, traffic analytics, and human-reviewed evidence events. It is a modular monolith, CPU-first, with a local filesystem and SQLite.

**The most important decision in this whole document:** speed estimation is only defensible if you have ground-truth speed to compare against. Most popular datasets (UA-DETRAC, BDD100K, KITTI) are not suitable for that. Your whole research contribution depends on solving the ground-truth problem (sections 12, 16, 17).

**My recommended direction:** a research paper on *error-decomposed, uncertainty-aware monocular speed estimation*. The product is the platform that makes those experiments reproducible.

## 2. Product Vision

- **Vision:** a trustworthy, reproducible, offline-capable workbench for turning traffic video into measured, auditable traffic facts.
- **Mission:** make every number traceable to a video, a calibration, a model version and a parameter set.
- **What differentiates it from "a vehicle detector with a web page":**
  1. Calibration is a first-class, editable, versioned object.
  2. Speed comes with an uncertainty estimate, not just a point value.
  3. Every run is an experiment record, so the paper's tables come straight from the database.
  4. Violations are review candidates, not verdicts.

## 3. Problem Definition

Camera-based speed and traffic analysis is usually done with closed, hardware-tied products, or with demo scripts that convert pixels to km/h using a single guessed scale factor. These give no error bounds and can't be reproduced or compared.

**Core research problem:** how accurately can vehicle speed be recovered from a single uncalibrated or weakly calibrated camera, which error sources dominate (calibration, detection anchor point, tracker, timing, smoothing), and how should uncertainty be reported?

**Core software problem:** a reproducible pipeline and workbench around that question.

## 6. User Journeys

1. **Analyze a clip:** create a project, upload a video, define calibration (click 4+ reference points, enter real distances), choose a config, run the job, watch progress, open the analysis workspace, view analytics, export a report.
2. **Run an experiment:** select a video/dataset, choose detector, tracker and speed method, run, then compare against ground truth on the experiment page.
3. **Review events:** open the event queue, view the evidence frame and clip, accept or reject with a note, export accepted events.

## 7. Functional Requirements (prioritized)

- **P0 (MVP):** video upload and validation; detection; tracking; manual calibration (homography from point pairs); speed per track; per-track and per-video CSV/JSON; annotated output video; basic analytics.
- **P1 (V1):** analysis workspace with overlays; experiment engine with ground-truth metrics; model registry; violation candidates plus evidence and review; PDF report; uncertainty estimates.
- **P2 (V2):** lane analysis, wrong-way detection, semi-automatic calibration, ANPR (optional), multi-video comparison.
- **Never build:** automated enforcement or legal fines, face recognition, live multi-camera fleets.

## 8. Non-Functional Requirements

- **Reproducibility:** each run stores config, code git hash, model hash, package versions and seed.
- **Determinism:** same input and config gives the same output (or documented tolerance).
- **CPU feasibility:** must run without a GPU. Target: offline batch processing, *not* a real-time claim. Any FPS figure must be measured and reported with hardware details.
- **Offline:** works with no internet after setup.
- **Security:** validated uploads, no path exposure, local-only by default.
- **Observability:** structured logs, job states, a health page.
- **Licensing hygiene:** every dependency and model has a recorded license.

**Ground-truth fallback plan (essential):**
1. **Synthetic videos** with known speed (Blender or a simple 3D renderer, free). This validates the *math*, since geometry error is fully known.
2. **Self-recorded clips** using a phone you already own (no purchase). Use known road-marking distances or tape-measured baselines, and a cooperating vehicle at a controlled speed. Speedometer ground truth is itself imperfect, so document its error.
3. **Timed gate ground truth:** measure real crossing times between two physical markers from video and compare.

Decision criteria, in order: license → CPU throughput at your target resolution → COCO-vehicle accuracy on your data → integration effort. ## 15. Tracking Selection Analysis

| Tracker | Why | Risks |
|---|---|---|
| **ByteTrack** | No appearance model, fast on CPU, strong on crowded scenes | ID switches at occlusion |
| **OC-SORT** | Better with non-linear motion, still cheap | Fewer maintained integrations |
| DeepSORT/StrongSORT | Appearance re-ID | Extra CPU cost; re-ID trained on other domains |
| SORT | Baseline | Weak at occlusion |

**Recommendation:** ByteTrack primary, OC-SORT and SORT as ablations. Implement a `Tracker` interface. For speed, ID stability matters more than MOTA: a switched ID corrupts a speed track. Track "fragmentation rate" as its own metric.

## 16. Speed Estimation Research

**Three distinct quantities, never conflate them:**

1. **Pixel displacement:** Δ(u,v) in the image. Meaningless as speed, because perspective makes the same pixel motion correspond to different real distances.
2. **Real-world distance:** requires mapping to a metric plane.
3. **Physical speed:** distance over *time*, and time must come from frame timestamps.

**Method:**
- Image → road-plane mapping: **homography H** (3×3), estimated from ≥4 point correspondences whose real-world distances you know. Point on plane: `[X,Y,1]ᵀ ∼ H·[u,v,1]ᵀ`.
- **Anchor point matters:** map a point *on the road* (e.g., bottom-center of the bounding box, or better a wheel-contact estimate), not the box center. The box center is above the plane and biases the result. Study this as an ablation.
- **Speed:** `v = ‖P(t₂) − P(t₁)‖ / (t₂ − t₁)`. Instead of two points, fit a line to `X(t), Y(t)` over a window (least squares); speed is the slope. Alternatives: Kalman filter on world coordinates.
- **Timing:** use presentation timestamps from the container, not an assumed constant FPS, because variable frame rate is common in phone and web video. Also handle frame dropping in your own pipeline.
- **Uncertainty:** propagate position noise σ and window length. For a two-point estimate, error scales like `√2·σ_pos/Δt`, so longer windows reduce noise but blur acceleration. Report a confidence interval per track (bootstrapping over the window, or propagated calibration error via perturbing reference points).
- **Virtual gates (alternative):** speed = known gate spacing ÷ crossing time. Cheaper, and a useful independent estimate.

**Metrics:** per-vehicle signed error (bias), MAE, RMSE, MAPE (careful at low speeds), fraction within ±X km/h, error vs distance from camera, and coverage of the reported intervals. BrnoCompSpeed defines its own protocol, and you should follow it where you use that dataset (**RV**).

## 17. Calibration Strategy

1. **MVP:** manual homography via reference points on lane markings with known lengths. Check the road authority's standard for dash lengths in your region before using them as a scale (**RV**). Otherwise measure them physically.
2. **V1:** intrinsic correction if lens distortion is visible (checkerboard, if you can print one for free), reprojection-error display, and a calibration quality score.
3. **V2:** semi-automatic calibration from vanishing points (Dubská et al.) with a single scale reference.
4. Store calibration as a versioned object with points, H, and its error estimate. Every speed result references a calibration version.

**Limits to be honest about:** flat-road assumption, uphill or curved roads, camera shake, and lens distortion all bias results.

## 18. Research Gap Candidates

1. **Error decomposition:** the literature usually reports one end-to-end error. A controlled attribution (calibration vs anchor point vs tracker vs timing vs smoothing) is more useful and feasible with an experiment engine. **Feasible, novel enough.**
2. **Uncertainty-aware speed:** interval outputs and calibration of those intervals. **Feasible.**
3. **Robustness to camera perspective/height:** vary synthetic camera pose and quantify degradation. **Feasible with synthetic data.**
4. **Mixed / Indian traffic (two-wheelers, autos, no lane discipline):** relevant, but you need data with ground truth. **Risky.**
5. **Fully automatic calibration:** ambitious; prior work exists. **Too big for MVP.**

## 19. Recommended Research Direction

Gaps 1 + 2 + 3 together: **"An error-decomposed, uncertainty-aware evaluation of monocular vehicle speed estimation."** Validate on synthetic data, then BrnoCompSpeed if you can get it, then your own clips. Novelty must be confirmed by a literature search. **RV.** Working title stays flexible.

## 24. System Architecture

**Modular monolith, two processes:** a FastAPI app (API plus static frontend) and a separate worker process that polls a `processing_jobs` table (no Celery, no Redis; add only if measured need appears). Both share the same Python package.

```
React SPA ──HTTP──► FastAPI (routers → services → repositories)
                       │                    │
                       │                    ▼
                       │                 SQLite (WAL)
                       ▼
                 jobs table ◄── polled by ── Worker process
                                              │
                                              ▼
                                   CV engine (pluggable stages)
                                              │
                                              ▼
                                   Local filesystem storage
```

Microservices are not justified. A `Storage` interface is enough for future S3.

## 25. CV Architecture

Pipeline as **independent, typed stages** with a config-driven registry:

`Decoder (PyAV/OpenCV, PTS timestamps) → Preprocess → Detector → Tracker → TrajectoryBuilder → Calibrator/Projector → SpeedEstimator → Analytics → ViolationRules → EvidenceWriter`

Improvements over your draft:
- **Two-stage processing:** stage A (detect + track) writes raw tracks to disk once. Stage B (calibrate → speed → analytics → violations) re-runs cheaply on stored tracks. This makes ablations over calibration and speed methods very fast, which is what the research needs.
- Frame skipping and resize are explicit, logged parameters.
- Every stage records timing.
- Region-of-interest and gates are part of the config.

## 26. Backend Architecture

- Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2 + Alembic, OpenCV, PyAV or FFmpeg (subprocess).
- Layers: `api/` (routers, schemas) → `services/` → `repositories/` → `models/`, with `cv/` and `worker/` isolated from the web layer.
- Job states: `queued → running → succeeded | failed | cancelled`, with progress, heartbeat and resumability where cheap.
- Structured JSON logging with run IDs; consistent error envelope; API prefix `/api/v1`.
- Config through `pydantic-settings` and `.env`.

## 27. Frontend Architecture

React + Vite + TypeScript, TanStack Query (server state), Zustand (small UI state), React Router, Tailwind + Radix primitives (shadcn/ui style, MIT), Lucide icons, charts via Recharts or Apache ECharts (both free; choose ECharts if you need many points).

**Video overlays:** draw on a `<canvas>` above `<video>`, synchronized using `requestVideoFrameCallback` and per-frame metadata. Note that the HTML video element is **not natively frame-accurate for stepping**. Options: (a) use frame-time metadata with `requestVideoFrameCallback` and accept small tolerance, (b) also render an annotated MP4 in the backend as the "guaranteed accurate" view. Do both. Overlay data is served in chunked JSON/NDJSON by time range, not one giant file.

## 28. Database Architecture

SQLite (WAL, foreign keys ON), Alembic migrations. Large per-frame data (raw tracks) lives as Parquet or compressed files on disk, indexed by the DB; the DB holds metadata and derived, queryable records.

```
users(1)─┬─(N)projects(1)─┬─(N)videos(1)─(N)processing_jobs(1)─┬─(N)tracks(1)─(N)speed_measurements
         │                │                                     ├─(N)violations(1)─(N)evidence
         │                │                                     └─(1)experiment_runs
         │                └─(N)calibrations (versioned)
models(1)─(N)model_versions ─(N)experiment_runs (N)─(1)datasets
reports ─ jobs ; system_events (standalone)
```

Key fields: every table has `id`, `created_at`, `updated_at`; jobs/experiments carry `status`, `config_json`, `git_hash`, `env_json`; tracks carry `class`, `first_ts`, `last_ts`, `file_ref`; speed measurements carry `method`, `calibration_id`, `value_kmh`, `ci_low/high`, `window`; violations carry `review_status`, `reviewed_by`, `note`. Skip a per-frame `frames` table for MVP (too large), and store it in files. Index on `(job_id)`, `(video_id)`, `(status)`, `(start_ts)`.

## 30. File Storage Architecture

```
data/
  datasets/   videos/   models/   outputs/   evidence/   reports/   experiments/
```
Files are addressed by opaque IDs (UUID/hash), never user-supplied names. The DB stores relative keys. A `Storage` interface (`put/get/open/delete`) has one local implementation; S3 is a later swap. Add a dataset manifest (SHA-256, source URL, license note) for each dataset.

## 31. Experiment Architecture

An experiment is a **frozen recipe**: dataset/video, detector+version, tracker+params, calibration version, speed method+params, seed. Running it writes an `experiment_run` with metrics, runtime, FPS, hardware (CPU/RAM/GPU), software versions, git hash and artifact paths. Metrics are computed by code against ground-truth files, never typed by hand. A comparison view and a `export_results.py` that emits LaTeX/CSV tables directly from the DB give you a paper whose numbers are traceable.

## 32. Model Management Architecture

`models` (logical: VehicleDetector) → `model_versions` (file hash, path, source, license, training dataset, metrics *measured by the experiment engine*, status: baseline/candidate/retired). No metric field may be filled unless it references an experiment run.

## 33. Security Architecture

- **Auth:** not needed for MVP (local, single-user). If the app will ever be network-exposed, add local login with argon2/bcrypt and two roles (Admin, Viewer). Four roles are not justified.
- Upload: extension *and* magic-byte check, ffprobe validation, size/duration limits, decode in a subprocess with timeout, randomized storage name, no serving of arbitrary paths.
- Path traversal: resolve and verify inside the data root.
- CORS to the known origin only, secrets from env, rate limiting only if exposed, no filesystem paths in API responses, log redaction.

## 34. Testing Architecture

`pytest` (unit, repository, API via TestClient, pipeline tests on tiny fixtures), golden-file tests for the homography and speed math using synthetic tracks with exactly known speed, Vitest + Testing Library (frontend), Playwright (end-to-end). Failure-case fixtures: corrupt file, empty video, unsupported codec, no vehicles, heavy crowd, night/low light, tracking loss, missing model, out-of-memory (simulated), job interrupted and resumed. CI on GitHub Actions free tier (limits **RV**).

## 35. DevOps Architecture

`pyproject.toml` (uv or pip-tools) with pinned lock, `pnpm`/`npm` lockfile, `Makefile` or `justfile`, pre-commit (ruff, black, mypy, eslint, prettier), `.env.example`, git-lfs *not* needed (keep large data out of git; document downloads). Docker: optional, added late; native local dev must work first.

## 61. Research Experiment Plan
